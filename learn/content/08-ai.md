# AREA ai | 10. The AI analyst | An LLM that may explain — but only with evidence, and only if it passes strict checks
FaultScope uses AI in exactly one place: **explaining** an experiment in words. Everything else (measuring, scoring, predicting) is plain code.

The rules that protect you from a confident-sounding wrong answer:
1. The model **only sees an evidence package** built by code from measured data (plus retrieved documents). It never sees a shell, Docker or the database.
2. Its answer must be **structured JSON** (root cause, findings with citations, recommended actions…).
3. A **grounding validator** rejects the answer if it cites evidence that doesn't exist, names a service that wasn't measured as affected, quotes a number that isn't in the evidence, recommends an action that doesn't address that fault, or leaves out an affected service.
4. One retry with the exact reasons fed back; if it still fails, the answer is shown as **rejected** (never as fact).
5. If the model can't be reached, you still get the deterministic, code-written summary (`llm_unavailable`).

> This is *RAG* — Retrieval-Augmented Generation: first **retrieve** relevant documents (runbooks, past experiment reports), then let the model **generate** an answer from them.

The flow: **question → link to an experiment → evidence package → retrieve documents → LLM → validate → store**.

## FILE app/ai/service.py | Orchestrates one analysis from question to stored result | code
### What it is
The coordinator. It ties together the knowledge base, the evidence builder, the LLM and the database.

### How it works
1. `link_question_to_experiment` — for a free-text question ("what happens when postgres is slow?") it finds the most relevant *finished fault experiment*: service aliases (`db` → postgres, `c++` → cpp-service…) score +3 if they match the experiment's target, +1 if they were affected; a matching fault-type word adds +1; later experiments win ties.
2. `start_analysis` checks the experiment is finished **and** has a blast-radius analysis, stores an `analyses` row (status `running`) that already includes the deterministic summary, and starts the job on a background thread (a local model can take a minute).
3. `run_job` builds the evidence (`prepare_evidence`), runs `run_analysis`, then saves status, diagnosis, errors, the evidence used, the model name, number of attempts and the retrieval mode.
4. `prepare_evidence` loads history (other signatures, same target/fault first), the resilience profiles, and **searches the knowledge base** with a query built from the fault type, target, question and symptom hints (errors → "5xx", slow → "latency p95", outages → "timeout").
5. Any exception marks the analysis `failed` with the reason — never silently swallowed.

## FILE app/ai/evidence.py | Builds the only thing the LLM is allowed to look at | code
### What it is
Pure code (no model). It assembles the **evidence package** — a dictionary of measured facts — and the list of **valid references** the model may cite.

### How it works
- `build_experiment_evidence` gathers: a code-written summary, the experiment settings, measured per-service facts (impact, p95 before/after, error %, status counts), the target, the end-user view, affected/direct/indirect services, propagation paths, recovery, warnings, past experiments (max 5), resilience profiles and up to 4 retrieved documents (trimmed to 700 characters each).
- `valid_refs` lists every legal citation, e.g. `measured.services.java-service`, `measured.end_user`, `history.0`, `resilience.postgres`, `doc.kb:runbooks/cpu-starvation#0`.
- `numeric_facts` collects every number that appears anywhere in the evidence (including numbers hidden in keys, like status code `502`). The validator uses this to catch **invented statistics**.
- `deterministic_summary` writes a plain-English summary with normal code, e.g. "End users: 100% of requests degraded (p95 44 ms → 7309 ms, 100% errors). Affected services: …". It is always available, even with no AI.

## FILE app/ai/analyzer.py | Prompts the model, validates, retries once | code
### What it is
Runs the conversation with the LLM. The `SYSTEM_PROMPT` states the rules plainly: answer only from the evidence, cite `VALID_REFS`, quote at least one measured number, never invent, include every affected service, explain the *mechanism*, and use an allowlisted action only when it really fixes this kind of fault.

### How it works
- `build_messages` puts the question, the list of valid references and the evidence JSON in the user message.
- `run_analysis` loops (max 2 attempts): call the model, parse the JSON, run `validate_diagnosis`. Accepted → return. Otherwise append the model's answer plus "Your answer was rejected for these reasons: …" and try again.
- Outcomes: **accepted**, **rejected** (reasons returned; raw output kept truncated, never shown as fact), **llm_unavailable** (model unreachable).

## FILE app/ai/schema.py | The required answer shape and the grounding validator | code
### What it is
The heart of "don't trust the LLM". Two things: the **schema** (what the JSON must look like) and **`validate_diagnosis`** (whether its content is honest).

### How it works — the schema
`Diagnosis` = `root_cause`, `confidence` (0–1), `affected_services`, `evidence` (each finding has a `claim` and at least one `refs`), `recommended_actions` (each with a `kind`: investigate / mitigate / prevent, and an `allowlisted_action`, one of five or `NONE`), `alternative_hypotheses`, `limitations`. The JSON Schema is hand-written (no `$ref`) because Ollama converts it into a grammar that forces valid output.

### How it works — the validator checks
1. Parses against the schema.
2. **Unknown references** — every cited ref must exist in the evidence.
3. **Unsupported services** — `affected_services` may only contain measured-affected services or the target.
4. **Omissions** — must include *every* measured-affected service.
5. **Measured citation** — at least one finding must cite a `measured.*` ref. Documents alone can't diagnose *this* experiment.
6. **Applicable actions** — an allowlisted action must address this fault type (via `action_for_fault`) or be `NONE`.
7. **Invented numbers** — every number in the root cause and claims must appear in the evidence (small whole numbers ≤ 10 are exempt as counts). Tolerance: 2 % or 0.5.

## FILE app/ai/llm.py | Talks to Ollama, the local model server | code
### What it is
Two small HTTP clients for **Ollama** (a program that runs language models on your own PC — no cloud, no API key, no cost):
- `OllamaClient.chat` sends messages to the model (`llama3.2:3b` by default) with `temperature 0.1` (mostly deterministic) and a JSON schema that constrains the output format.
- `OllamaEmbeddings.embed` turns text into vectors using `nomic-embed-text` (used for semantic search).

### How it works
Every failure becomes `LLMUnavailable`. **The code never fabricates output when the model is down.** `parse_json_object` tolerates the model wrapping JSON in a code fence, but anything else that isn't a JSON object raises an error.

## FILE app/ai/retrieval.py | Search: BM25 keywords + optional embeddings, merged | code
### What it is
Pure search code, no database or network. Two ways to rank documents, then merge:

- **BM25** — the classic keyword ranking. It rewards rare terms that appear in a chunk (a term like `cpp-service` matters more than `the`) and normalises for chunk length. Great for exact technical names.
- **Dense (embedding) search** — each chunk becomes a vector of numbers; similar meaning = similar vector (cosine similarity). Catches paraphrases BM25 misses.
- **Reciprocal Rank Fusion (RRF)** merges the two rankings: each item scores `1/(60 + rank)` per list; the sums decide.

### How it works
- `tokenize` lowercases, removes stopwords, and keeps hyphenated names whole **and** split (`cpp-service` → `cpp-service`, `cpp`, `service`).
- `chunk_text` splits Markdown at headings first, then at paragraphs, keeping each chunk ≤ 900 characters so retrieved pieces are focused.
- With no embedding model, BM25 alone is used and the system **says so** (`retrieval: bm25`).

## FILE app/ai/knowledge.py | The searchable library: runbooks, architecture, and past experiments | code
### What it is
`KnowledgeBase` indexes three kinds of documents: the Markdown files in `knowledge/` (architecture + runbooks), and an **auto-generated report for every analysed experiment** — institutional memory that grows with each run.

### How it works
- `load_repo_documents` reads the Markdown files; runbooks get `source=runbook`.
- `experiment_report` writes a deterministic report (summary + one line per service + hypothesis + warnings).
- `_upsert` stores chunks in the `knowledge_chunks` table and skips documents whose content hash hasn't changed.
- `_embed_missing` asks Ollama for embeddings of chunks that lack one — only if an embedding model is available.
- `_rebuild` loads everything into memory (BM25 index + vectors).
- `search` = BM25 (+ dense if available) → RRF → chunks labelled `doc.<chunk id>` — exactly the references the model may cite. If embeddings fail, it falls back to BM25 alone.
- `retrieval_mode()` reports `none`, `bm25` or `hybrid` honestly.
